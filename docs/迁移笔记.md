## 一、DSH 会话存在哪

```
~/.dsh/sessions/--<工作目录slug>--/session-<uuid>/session.v4.jsonl.zstd
```
- zstd 压缩的 JSONL，每行 `{type, seq, time, data}`
- 类型：`user/message`、`assistant/message`、`tool/call`、`tool/result`、
  `compaction/summary`、`turn/start|end`、`job/*`、`workspace/changes` …
- 本次会话：191 MB 解压后 / 28329 行 / 用户 772 条 / 助手 2995 条 / 工具调用 3698 次

## 二、WorkBuddy 会话是什么格式

实测（读 `~/.workbuddy/projects/*/*.jsonl` 与 `~/.workbuddy-ai/projects/*/*.jsonl`）：

```
<home>/projects/<项目slug>/<session-uuid>.jsonl     ← 会话正文
<home>/workbuddy.db 表 sessions                     ← 会话索引（UI 靠它列出）
```
每行一个事件，靠 `parentId` 串成链：

| 事件 | 关键字段 |
|---|---|
| `session-meta` | `meta:{"codebuddy.ai/hostKind":"unopted"}` |
| `message` | `role:user\|assistant`, `content:[{type:'input_text'\|'text', text}]` |
| `reasoning` | `rawContent:[{type:'reasoning_text', text}]` |
| `function_call` | `name`, `arguments`(JSON 字符串), `callId` |
| `function_call_result` | `name`, `callId`, `status`, `output:{type:'text',text}` |
| `ai-title` | `aiTitle` |
| `file-history-snapshot` | 文件改动快照（可选） |

`sessions` 表里 coding 会话的参照值（实测样本）：
`source_mode='coding'`、`is_playground=1`、`mode='craft'`、`transport='local'`、
`permission_mode='bypassPermissions'`、`use_sandbox_cli=1`、`thought_level='high'`、
`addon_selection='{"version":1,"welcomeMode":"coding","interactionMode":"craft","permissionMode":"bypassPermissions"}'`

## 六、第二轮（13:30 之后）——找到第一次为什么 UI 不显示

第一次导入的会话 UI 不出现，原因不是「应用没启动」，而是**两处写错**：

| 文件落点 | `projects/c-DeepSeekHarnessWork/` | `projects/d-DeepSeekHarnessWork/`（slug 由 cwd 推） |

UI 按「当前账号 + 当前工作区 cwd」过滤会话，两处都不匹配 → 一条也看不到。

### 还踩到一个坑：多帧 zstd

`session.v4.jsonl.zstd` 是**多帧** zstd（一个事件一帧，191 MB 的会话有上千帧）。
`zlib.zstdDecompressSync()` / `createZstdDecompress()` **只解第一帧**，解出来永远只有 203 字节的 session 头 —— 这就是上一轮 `export_session.js` 对小会话「只有 1 行」的原因。
正确做法：按 magic `28 B5 2F FD` 切帧，逐帧解压，解不开就与下一帧合并重试（防 magic 出现在压缩数据内）。

## 新增的两条硬规则

1. **归档会话默认不导**。DSH 归档名单在 `~/.dsh/storages/workspace.json` 的
   `global.archivedSessionIds`（带 `session-` 前缀）。当前 10 条里 5 条是归档的，

2. **两个方向都不静默覆盖**。目标已存在同 id 时跳过并提示，`--overwrite` 覆盖、`--new-id` 另存。

## 反向导出（WorkBuddy → DSH）怎么落盘

- 会话文件：`~/.dsh/sessions/--<cwd slug>--/session-<uuid>/session.v4.jsonl.zstd`，**每个事件压成一帧**
- 注册：写 `workspace.json`，把 id 塞进对应工作区的 `sessionIds`，并从 `archivedSessionIds` 摘掉
- **不写 `session_projcache`**：app.asar 内文档明确「缺失或过期的记录一律读作不存在，
  需要冷值的消费方自己从日志重建」→ 让 DSH 自己重建，避免伪造版本化投影
- 事件骨架按真实日志拼：`turn/start → step/start → user/message →（tool/call、tool/result）→ assistant/message → step/end → turn/end`，
  每条用户消息算一个 turn；工具调用前的推理会单独落一条只有 `reasoning` 的 `assistant/message`，否则会丢

## 十、修一个硬错误：`surfaceOp`

第一次反向导出后 DSH 打开直接报：

```
SessionFormatError: user/message surfaceOp requires an object
```

从 `app.asar` 里翻到校验代码，规则是：

```js
SURFACE_EVENT_TYPES = ['system/message','developer/message','user/message','assistant/message','tool/result']
surfaceOpOf(event):
  if (!isSurfaceEligibleType(type)) { ...不许带 surfaceOp... }
  if (op === undefined) throw 'requires a surfaceOp marker'
  if (op === 'append') return op            // 字符串就合法
```

也就是说这 5 类事件**必须**带顶层 `surfaceOp:'append'`，其余事件**不许**带。
之前只写了 `type/seq/time/data`，于是 DSH 读日志即失败 —— WorkBuddy 回读没事，是因为我们自己的解析器不校验。

修法：`wb2dsh.js` 落盘前给这 5 类补齐 `surfaceOp:'append'`；
另加 `scripts/verify.js` 复刻读取器的硬约束（surfaceOp / seq 递增 / replace 引用范围 / 各类型必填字段 / turn-step 配对），
`wb2dsh.js` 写完自动跑一遍，不合格直接退出码 4，不再把坏日志交给 DSH。

现在 `node verify.js --all` 对 11 个会话（含两条 10 万级真实会话 + 我们导出的那条）全绿。

## 十一、再修一个硬错误：工具生命周期

`surfaceOp` 之后又撞上：

```
SessionFormatError: tool/call call_00_YrsF… has no advertised tool lifecycle
```

asar 里 `foldSurface` 维护一张 `toolLifecycles`：

| 事件 | 作用 |
|---|---|
| `assistant/message` 的 `content[].type==='tool-call'`（`{id,name,arguments}`） | announce，state=`advertised` |
| `tool/call`（同 id，`name`/`arguments` 必须**字符串全等**） | state → `started` |
| `tool/result`（`surfaceOp:'append'`） | 删除该条；`replace` 型不参与 |
| `step/end` / `turn/end` | `assertNoUnresolvedTools` 后清表 |

原来的导出把 `tool/call` 直接挂在 assistant 文本之后，没有 announce，所以整条会话读不出来。
现在的写法：把一批 `function_call` 攒起来，先发一条带 `tool-call` 块的 `assistant/message` 做 announce，
紧接着 `tool/call` + `tool/result`，再 `step/end`；只有文本答案单独占下一个 step。

顺手对齐的两个细节：
- `agent/inbox/spliced` 里插入的条目 id 与随后 `user/message` 的 `data.id` 必须相同
- 助手文本后面若还有工具调用，就留在同一个 turn 里开新 step，不提前 `turn/end`

`verify.js` 现在同时校验生命周期与收件箱 id 一致性；`node verify.js --all` 11 个会话（含两条 10 万级真实会话）全绿。
